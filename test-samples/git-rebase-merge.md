# Git Rebase 与 Merge 的选择

## 背景

在团队协作中，当本地分支落后于远程主干时，开发者需要在 rebase 和 merge 之间做出选择。两者都能把别人的提交整合进自己的分支，但产生的历史形状完全不同。

## Merge 的工作方式

`git merge main` 会创建一个新的"合并提交"（merge commit），它有两个父提交。历史图上会出现分叉再汇合的菱形结构。merge 保留了真实的协作时间线：谁在什么时候从哪里分出去、又在哪里合回来，一目了然。缺点是历史图会变得复杂，长期使用 merge 的主干像意大利面。

## Rebase 的工作方式

`git rebase main` 会把你分支上的提交逐个"摘下来"，放到 main 的最新提交之后重新提交，生成一串全新的 commit hash。历史变成一条直线，干净整洁。代价有两点：一是改写了历史，新提交与原提交内容相同但 hash 不同；二是如果分支已经推送到远程并有他人在用，rebase 会让协作者混乱，通常被禁止。

## 什么时候用哪个

一个被广泛接受的实践是：在个人分支内部同步主干变化时用 rebase，保持分支历史线性；在把个人分支合入主干时用 merge --no-ff，保留一次明确的合并记录，方便整体回滚。GitHub 上的 PR 默认就是生成 merge commit。

## Golden Rule

Rebase 的黄金法则：不要对已经推送到共享仓库的提交执行 rebase。一旦提交被别人拉取过，改写历史就会造成冲突和重复提交。如果 rebase 出错，可以通过 `git reflog` 找到 rebase 之前 HEAD 的位置并恢复。

## 小结

merge 保真但历史复杂，rebase 整洁但有改写历史的风险。理解两者对 commit 历史的不同影响，比记住命令本身更重要。
