## 卡片 1：Merge 的本质

**核心知识**：`git merge` 会创建一个拥有两个父提交的合并提交，在历史图上形成分叉再汇合的菱形结构。

**解释**：merge 保留了真实的协作时间线：谁在什么时候从哪里分出去、又在哪里合回来，一目了然。代价是长期使用后，主干的历史图会变得像意大利面一样复杂。

**例子**：原文中 `git merge main` 产生的合并提交拥有两个父提交，正是历史图上菱形结构的汇合节点。

## 卡片 2：Rebase 的本质

**核心知识**：`git rebase` 把分支上的提交逐个"摘下来"，放到目标分支最新提交之后重新提交，使历史变成一条直线。

**解释**：rebase 之后的历史干净整洁。但新提交与原提交内容相同、commit hash 却是全新的，等于改写了历史。

**自测**：rebase 之后，分支上原有提交的 hash 还和原来一样吗？

## 卡片 3：Rebase 与 Merge 的推荐分工

**核心知识**：个人分支内部同步主干变化时用 rebase，把个人分支合入主干时用 merge --no-ff。

**解释**：前者保持分支历史线性；后者保留一次明确的合并记录，方便整体回滚。GitHub 上的 PR 默认就是生成 merge commit。

**例子**：原文给出的组合实践——"rebase 同步主干 + merge --no-ff 合入主干"。

## 卡片 4：Rebase 黄金法则

**核心知识**：不要对已经推送到共享仓库的提交执行 rebase。

**解释**：一旦提交被别人拉取过，改写历史就会造成冲突和重复提交。这条法则也解释了为什么"分支已推送且有他人在用"时 rebase 通常被禁止。

**自测**：如果一个分支已经推送到远程且同事正在基于它开发，可以对它 rebase 吗？

## 卡片 5：Rebase 出错的恢复方法

**核心知识**：如果 rebase 出错，可以通过 `git reflog` 找到 rebase 之前 HEAD 的位置并恢复。

**解释**：reflog 记录了 HEAD 的移动轨迹，即使提交被 rebase 改写，仍能在 reflog 中定位到改写前的位置，从那里恢复分支。

**自测**：rebase 之后发现搞砸了，用什么命令可以找到操作前的 HEAD 位置？

## 卡片 6：如何选择 Rebase 与 Merge

**核心知识**：merge 保真但历史复杂，rebase 整洁但有改写历史的风险。

**解释**：两者的本质差异在于对 commit 历史形状的不同影响。理解这种影响，比记住命令本身更重要。
